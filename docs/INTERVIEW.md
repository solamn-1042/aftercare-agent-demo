# 售后 Agent：项目讲解与面试问答

证据版本：2026-11-14，v2 Case Lab。准备思路参考 [JavaGuide Agent 项目面试指南](https://javaguide.cn/ai/interview-questions/agent-project-interview-guide.html)，回答和数值来自本仓库实现与实测，不把指南中的示例当成本项目经历。

这是一份可演示、可追问的项目底稿。代码由AI辅助实现与测试；以下“我”的讲法须建立在自己跑过、读懂对应代码的基础上。没有生产上线、真实客户数、节省人力或支付成功率可供宣称。

## 给HR的30秒介绍

我做了一个售后咨询和工单处理项目。它能根据订单找到正确渠道和版本的政策，检查申请条件，再生成需要用户确认的工单草稿。我重点补的是普通问答之外的业务可靠性：防越权、防重复提交，以及出错后能查清实际结果。项目有可操作页面、自动测试和评测记录，可以现场演示政策检索优化和重复确认不重复建单。

追问“有什么难度”时：难点不是让模型说出一段答案，而是防止它引用不适用的规则、承诺并不存在的能力，或者重复执行一个业务动作。每个难点都有具体的失败输入和回归证据。

## 三分钟技术介绍

1. **场景与完成条件**：用户说耳机坏了，不一定知道订单号或售后要求。任务完成不是“模型说申请成功”，而是有正确用户、订单、问题类型和政策依据的工单记录；信息不足就追问，超期或缺照片就停止自动申请。
2. **一次请求**：HTTP鉴权得到服务端身份→读取会话中的已确认订单→局部LangGraph循环选择订单、政策和资格工具→生成待确认草稿→用户点击确认→重新校验身份、摘要、期限和版本→事务写入工单→按动作ID返回结果。结构化页面可以不经过模型完成同一业务流程。
3. **关键选择**：模型只做不确定的工具选择；写入采用确定性工作流。SQLite适合单进程演示，唯一约束和事务比“提示模型不要重复提交”可靠。政策先按适用范围过滤，再做BM25，先解决拿错版本的问题；没有为了堆技术直接加入多Agent和Reranker。
4. **失败与修复**：全库检索把其他渠道政策混进来，加入元数据过滤后90条留出题Hit@3从30%到90%；真实模型还曾提示页面上传照片，但页面没这个能力，因此根据业务状态约束最终回复并加入回归。
5. **结果与边界**：57项自动回归通过，真实模型8个任务各3次的草稿状态检查通过，但不能叫回答准确率100%。数据是合成的，仍有9条口语召回失败；没有真实退款、生产流量和独立人工评分。

## HR常见追问

### 这个项目解决了什么具体问题？

同一句“耳机坏了”，不同购买渠道、购买时间和签收天数，适用规则可能不同。项目把“检索到相关文字”和“这笔订单能申请”分开，避免模型用通用规则直接作出承诺。用户确认后还必须有可查询的工单状态，而不是只收到一句成功回复。

### 与网上的聊天Demo有什么不同？

可以现场展示旧政策与当前政策的选择、他人订单拒绝、超期停止、待确认草稿、重复确认只返回一张工单，以及重启后恢复草稿。它仍然是个人Demo，但这些业务约束和测试让工程能力有具体证据。

### 你最有价值的一次优化是什么？

将订单元数据用于检索前过滤。在相同语料、问题和BM25排序器下，90条留出题Hit@3由27/90变为81/90，错误适用范围片段225个变为0。收益来自减少错误候选，不是换大模型；代价是依赖正确订单数据，用户未提供订单就不能擅自推断渠道。

### 为什么没有真实用户？项目价值怎么证明？

当前用可复现任务、自动回归、故障注入和页面演示证明设计能运行。不能证明商业收益和生产稳定性，也不编造用户数。下一步需要独立标注、真实脱敏问题分布和受控试点。

### 能给我现场演示吗？

按DEMO.md操作：正常申请→对照政策→确认→重复确认→查看同一工单号，再切换B001展示权限拒绝。只需要本机服务和演示令牌；自然语言环节需模型配置，结构化流程不依赖模型可用性。

## 架构与技术追问

### 为什么保留规则流程，又引入Agent？

单纯自然语言入口不能证明必须用Agent。本项目表单路径完全能由规则完成，因此保留它作为可解释对照。Agent用于从不完整描述选择读取订单、检索、检查或追问；写操作仍由固定工作流控制。目前没有完成与“意图分类+表单”的同数据对照，不能声称Agent必然更优。

### 为什么不直接做多个Agent？

目前只有4个工具，一个领域、一份状态，拆分会增加模型请求和排障路径。先证明单Agent的边界和工具契约有效。只有不同团队/业务域需要隔离上下文或权限时，才有证据考虑多Agent。

### 一轮请求中哪些数据是权威来源？

订单和工单以SQLite为准；资格以代码和适用政策为准；会话只记已确认订单；检索提供外部证据；模型上下文是这些材料的一次组装。模型文字不能改订单owner、批准资格或更新工单状态。模型不会得到confirm工具。

### 你真的做了Memory吗？

只有持久化的短期会话订单绑定，24小时闲置到期。没有长期偏好、自动记忆写入或全量聊天历史。换会话不会继承订单；越权订单不能绑定。相关证据在session、bind及隔离测试。

### 模型和框架为什么这样选？

已有兼容DeepSeek的配置用于真实工具调用基线，LangGraph明确表达model/tools循环。不是评测后证明该模型最优；目前没有多供应商成本质量对照。框架负责节点执行和类型协议，业务一致性由自己写的Workflow负责。

### 为什么v2没有沿用向量检索做全部演示？

原v1保留BGE/Chroma及混合检索。v2这轮故意控制排序器，用同一BM25隔离“适用范围过滤”的因果作用，也让无模型下载的展示可以启动。代价是口语语义召回较弱。下一步应在同一冻结数据集比较向量、混合和Reranker，不将旧14片段测试与新248记录混报。

### 如何证明不是在测试集上调到90%？

脚本按商品族划分150条开发题和90条有答案测试题，算法没有使用gold答案ID；报告保存语料和用例指纹。测试题和文档仍由同一作者生成、存在模板结构，严格意义上不是独立第三方盲测。90%只适用于这套合成数据，9条失败保留在报告中。

### 100%权限过滤是否说明安全已经完整？

否。内部记录在代码中无条件排除，订单另验owner。测试只验证已知边界；单Bearer映射固定用户并不是完整租户认证。部署到公网需要组织身份、动态owner映射、速率限制、访问审计和安全评审。

### 哪些地方有缓存？怎样防串数据？

只缓存公开政策检索结果，key含语料指纹、问题、商品、渠道、购买日期、检索模式和Top-K，最多256项LRU，并返回深拷贝。订单、资格和工单不缓存。政策版本变化造成cache miss，确认还会重读业务状态。测试覆盖不同渠道与版本、缓存被调用方修改以及容量上限。

### 为什么不接Redis？

单进程Demo没有跨副本共享缓存需求；加入Redis会增加部署和运维成本。若扩多副本，应先解决集中身份、数据库、限流和模型配额，再讨论缓存共享，不能只换缓存就称为分布式。

## 可靠性与安全追问

### 一次写操作有哪些校验？

服务端身份→本人订单→问题类型和描述Schema→申请窗口→保存带摘要的草稿→用户点击确认→再次验owner、摘要、15分钟期限、订单revision、政策指纹及Schema→数据库事务与唯一约束→持久化工单号。草稿取消后不能确认；过期或版本变化必须重新准备并确认。

### 为什么超时后不能直接新建一个请求？

超时可能发生在写入已完成之后。测试故意在事务提交后抛TimeoutError，查询原Action ID可以看到SUCCEEDED；重复确认返回原ticket_id。生成新ID盲重试会丢失关联，因此逻辑动作ID应在恢复中复用。本Demo还用(owner,order,issue)唯一约束防不同草稿重复申请。

### SQLite怎样处理同时点击？

确认使用BEGIN IMMEDIATE串行化写事务，5秒busy timeout，加动作唯一键和业务唯一键。8次并发确认覆盖同一/不同草稿，最终只生成一个工单号。代价是写并发低；这是单节点一致性，不是分布式Exactly-once。

### 用户等很久或服务重启怎么办？

草稿、摘要、run ID、action ID、策略版本和到期时间在数据库。用户拿Action ID重新查询，服务恢复后仍可看到状态。确认时重新校验；不靠原进程内存或聊天文字恢复。测试用新Workflow实例打开同一数据库验证。

### 如何限制死循环、延迟和费用？

最多4次模型、6次唯一工具调用、每轮2工具，重复规范化参数会报无进展；调用前检查20秒预算，模型请求最多8秒且不自动重试，输出最多500 Token。记录实际Token但未实现按价格计算的总费用硬限制。Python线程不能强杀所有底层I/O，20秒是调度预算而非严格实时SLA。

### 模型不可用时怎么办？

返回provider_error或未配置状态，保留可用的结构化工作台。没有伪造自然语言回答，也没有未经评测的备用模型。实际需要熔断和自动降级时，应先建立同任务集的备用模型质量基线。

### Prompt Injection怎么处理？

模型不能传owner字段，严格Schema拒绝额外字段；查订单重新验owner；内部文档在检索前排除；不向模型开放confirm。Prompt只补充行为说明，不能代替代码授权。没有声称彻底解决所有注入问题，尤其自然语言事实蕴含仍需评分与约束。

### Trace里保存了什么？

request ID标识HTTP请求；session ID关联短期订单；run ID关联一次Agent任务；tool call ID关联具体调用；action ID在确认和恢复中稳定。持久化的模型Trace只含节点、调用名/ID、状态和耗时，保留7天，不存思维链或完整Prompt。工单审计事件记录准备、确认、取消与结果，可由run ID查询。业务草稿仍保存描述，生产隐私治理尚未完成。

## 两类Badcase的复盘

### 效果问题：相关政策不等于适用政策

- 输入：某商品的故障咨询，订单属于特定渠道和购买日期。
- 现象：全库BM25把同商品其他渠道/旧版本放入Top-3。
- 根因：排序器只看文本相关性，没有适用性过滤，不是模型“不够聪明”。
- 控制变量：语料、问题、ACL、分词和Top-K不变，仅加入商品/渠道/日期预过滤。
- 结果：留出集27/90→81/90；范围错误片段225→0。
- 代价与遗留：不能从模糊输入猜渠道；“开不了机”等口语仍会漏召回，需后续语义检索实验。
- 证据：lab_report.json逐题命中ID、scope_violations及failures。

### 能力越界：不存在的照片上传入口

- 首轮真实模型在photo任务中要求“在页面上传照片”；实际只有描述输入，没有上传功能。
- 结构化检查仍通过，因为它只检查没有错误建单；说明指标覆盖面不够。
- 修复放在业务输出边界：shipping资格检查后使用明确的人工核验说明；不再让模型凭空承诺上传和提交。
- 测试：注入同样的错误模型回复，断言最终不含虚假能力承诺；8任务各3次再跑一轮。
- 限制：这不是完整事实验证器，其他任意措辞仍可能出错；最终答案质量不能由草稿状态推导。
- 证据：evals/baseline/lab_agent.json、evals/lab_agent.json、test_photo_case_does_not_advertise_nonexistent_upload。

### 工程问题：写入已成功，但返回响应丢失

- 测试在本地事务提交之后注入超时，模拟调用方不知道最终状态。
- 通过稳定Action ID查询到原工单，重复确认返回同一对象；参数摘要不一致则拒绝。
- 这是明确标记的故障注入，不是线上事故，不等于已经接入外部退款平台。
- 证据：test_response_loss_then_recovery_returns_one_ticket、test_concurrent_confirm_and_multiple_drafts_deduplicate。

## 指标口径：面试中必须讲清

完整数值见METRICS.md。Hit@3分母是90条有答案留出题，不含12条无答案题；命中要求精确Gold政策ID，不是“任意相关文档”。MRR@3没命中记0。范围错误数统计返回片段，不是问题数。24次模型结构检查验证预期草稿状态及未确认不写入，不检查所有语义，因此绝不称“模型准确率100%”。

原v1平均1.90秒与v2约3.94秒的任务、工具和运行方式不同，不能拿来计算性能退化或提升。新缓存实验只说明重复检索CPU耗时变化，绝不能说端到端模型响应提升同样比例。

## 规模扩大或上线前还缺什么

优先考虑模型配额和延迟、SQLite单写锁、进程内并发槽及缓存。多副本要集中身份、限流和业务状态，采用服务型数据库；外部写入要有提供方幂等键、状态查询与对账。还需独立人工评测、真实脱敏问题、无答案校准、语义检索/重排对照、数据保留和删除、HTTPS及运维告警。没有压测十倍流量，不能把这些判断说成已定位的生产瓶颈。

## 面试前亲自完成的检查

- 亲自运行一次安装、检索评测和测试，能解释一个失败用例。
- 在页面创建、取消、恢复草稿，重复确认并查数据库。
- 读懂workflow.confirm的事务边界，说明为什么把确认工具给模型是不够的。
- 打开两轮photo任务结果，复述“状态检查通过但文本仍有错”。
- 能说明BGE/Chroma属于v1，v2这轮对照是BM25+范围过滤，不混报技术和收益。
- 讲自己理解、修改和验证过的内容；不把生成的讲稿当作已独立掌握全部实现的证明。
